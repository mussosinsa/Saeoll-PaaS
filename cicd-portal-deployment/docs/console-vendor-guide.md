# CI/CD 콘솔 업체 가이드 (개발 · 배포)

업체 개발자가 CI/CD 콘솔(`https://cicd.<도메인>`)로 **소스를 올리고, 빌드·배포 상태를 보고, 운영 배포를 요청하는 방법**을
처음 하는 사람 기준으로 설명한다. 이 환경의 `<도메인>` = `192.168.20.151.nip.io`.

이 문서는 **K-PaaS SCM + Jenkins** 업체 기준이다. GitLab 업체는 다른 점을 [8장](#8-gitlab-업체라면)에 따로 적었다.
더 자세한 git·Jenkins 사용법은 [SCM 개발자 가이드](vendor-guide-scm.md)를 본다.

---

## 0. 한눈에 보기

```text
내 PC ── git push (develop) ──▶ SCM 저장소 ──(5분 안에 자동)──▶ 빌드 ──▶ dev 자동 배포 ──▶ 테스트
                                                                            │
내 PC ── git tag v1.0.0 push ──▶ 콘솔 [릴리스] ──▶ 릴리스 빌드 ──▶ 운영 관리자에게 요청 ──▶ prod 배포
```

| 이름 | 주소 (예: 업체 `saeoll`, 앱 `homepage`) |
| --- | --- |
| CI/CD 콘솔 | `https://cicd.<도메인>` |
| 소스 저장소 웹 화면 | `https://scm.<도메인>` |
| git 주소 | `https://scm-manager.<도메인>/scm/git/saeoll-homepage` |
| dev 서비스 | `https://homepage-saeoll-dev.<도메인>` |
| prod 서비스 | `https://homepage-saeoll.<도메인>` |

콘솔에서 **할 수 있는 것**: 우리 업체 앱 보기, develop 빌드 실행·중지, 빌드 로그 보기, dev 배포(Sync), 릴리스 빌드.
**운영 관리자에게 요청할 것**: prod 배포, 롤백, 새 앱 추가, DB 연결, 구성원 추가, 비밀정보(접속 키 등) 등록, 보안 예외 승인.

---

## 1. 운영 관리자에게 받는 것

- 계정 ID와 임시 비밀번호 (예: `saeoll-hong`)
- 인증서 파일 `ca.crt` (사설 인증서. 브라우저·git이 신뢰하도록 설치)
- 앱 이름과 git 주소

---

## 2. 처음 로그인하기

### 2-1. 콘솔 로그인

1. 브라우저로 `https://cicd.<도메인>` 접속
   - "연결이 비공개로 설정되어 있지 않습니다" 경고가 나오면 `ca.crt`를 설치한다
     (Windows: `ca.crt` 더블 클릭 → 인증서 설치 → 로컬 컴퓨터 → **신뢰할 수 있는 루트 인증 기관**). 급하면 **고급 → 계속**.
2. Keycloak 로그인 화면에서 계정 ID / 임시 비밀번호 입력 → 새 비밀번호로 변경
3. 대시보드에 우리 업체(`saeoll`)와 앱이 보이면 성공

> "접근할 수 있는 업체가 없습니다"가 나오면 운영 관리자에게 업체 구성원 추가를 요청한다. 추가된 뒤에는 **로그아웃 → 다시 로그인**.

### 2-2. git 비밀번호 설정 (소스 저장소)

SCM 저장소는 로그인 비밀번호와 **다른 git 비밀번호**를 쓴다.

1. `https://scm.<도메인>` 로그인 (같은 K-PaaS 계정)
2. 오른쪽 위 계정 이름 → **내정보 관리** → **비밀번호 변경** → 새 비밀번호 입력
3. 이 비밀번호를 git clone/push 때 사용한다.
4. 처음 로그인했다고 운영 관리자에게 알린다(그래야 저장소 **참여자(쓰기)** 로 추가할 수 있다).

## 3. PC 준비와 소스 받기

Git이 설치되어 있어야 한다(Windows: Git for Windows, 아래 명령은 **Git Bash**에서 실행).

```bash
# 1) 인증서 등록 (ca.crt 를 홈 폴더에 kpaas-ca.crt 이름으로 저장했다고 가정)
git config --global http.https://scm-manager.<도메인>/.sslCAInfo ~/kpaas-ca.crt

# 2) 내 이름 등록
git config --global user.name "홍길동"
git config --global user.email "hong@example.com"

# 3) 소스 받기 - 반드시 develop 브랜치로
git clone -b develop https://scm-manager.<도메인>/scm/git/saeoll-homepage
#   Username: 계정 ID (saeoll-hong)   Password: 2-2의 git 비밀번호
cd saeoll-homepage
```

저장소에는 처음부터 샘플 소스가 들어 있다. 꼭 지켜야 할 규칙:

| 규칙 | 내용 |
| --- | --- |
| 포트 | 앱은 **8080** 포트로 응답 (`Dockerfile` 유지) |
| 헬스 체크 | `GET /healthz` 가 200 응답 (PHP는 `/healthz.php`). 없으면 배포가 `오류`로 표시된다 |
| `Jenkinsfile` | 빌드 방법. 위쪽의 `buildScript`, `testScript` 정도만 수정 |
| 브랜치 | `develop` = dev 자동 배포, `main` = 운영 기준, 작업은 `feature/<이름>` |
| 비밀정보 | 비밀번호·키를 소스에 넣지 않는다. 운영 관리자에게 등록 요청 |
| DB | DB 접속 정보는 환경 변수 `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`로 받는다 |

## 4. 콘솔 화면 읽는 법

### 4-1. 대시보드와 업체 화면

- **대시보드**: 우리 업체의 앱별 dev / prod 상태와 배포된 이미지 태그.
- 업체 이름을 누르면 **업체 화면**: 앱 카드(최근 빌드, dev, prod), **구성원**, **업체 정보**(네임스페이스, 리소스 사용량).

### 4-2. 앱 화면

앱 이름을 누르면 다음이 보인다.

**파이프라인 (5단계)**

| 단계 | 의미 | 버튼 |
| --- | --- | --- |
| 1. 소스 | develop 브랜치가 빌드 대상 | |
| 2. 빌드 · 이미지 | 최근 develop 빌드 결과 | **빌드 실행** |
| 3. dev 배포 | dev 환경 상태와 이미지 태그 | **Sync** |
| 4. 릴리스 | 최근 릴리스(운영용) 빌드 결과 | **릴리스** |
| 5. prod 배포 | 운영 환경 상태 | 운영 관리자만 |

**빌드 이력**: 번호, 구분(dev/릴리스), 브랜치·태그, 상태, 시간. **로그**를 누르면 빌드 로그가 실시간으로 나온다.

**dev 환경 / prod 환경**: 이미지, 접속 주소, 리소스(Deployment·Service 등) 상태, 배포 이력.

### 4-3. 상태 표시 뜻

| 표시 | 뜻 |
| --- | --- |
| 성공 / 실패 / 실행 중 / 대기 / 중지됨 | 빌드 결과 |
| 정상 | 앱이 잘 떠 있음 |
| 진행 중 | 배포 중 (잠시 기다림) |
| 오류 | 앱이 뜨지 않거나 헬스 체크 실패 → 9장 |
| 없음 | 아직 배포된 것이 없음 (첫 빌드 전) |
| 동기화됨 | 설정대로 배포되어 있음 |
| 변경 있음 | 새 버전이 준비되었지만 아직 배포되지 않음 (prod는 운영 관리자 배포 대기) |

## 5. 개발하고 dev에 배포하기

```bash
git checkout develop && git pull                 # 최신 받기
git checkout -b feature/login                    # 작업 브랜치
# ... 개발, 로컬 테스트 ...
git add . && git commit -m "로그인 화면 추가"
git checkout develop && git merge --no-ff feature/login
git push origin develop                          # dev 배포 시작
```

1. push 후 **5분 안에** 빌드가 자동으로 시작된다. 바로 하고 싶으면 콘솔 앱 화면 → **빌드 실행**.
2. 앱 화면 **빌드 이력**에 `실행 중`이 보이고, 화면은 15초마다 저절로 새로 고쳐진다. 진행 상황은 **로그**에서 본다.
3. 빌드가 **성공**하면 1~3분 안에 **3. dev 배포**의 이미지 태그가 `dev-<커밋>-<번호>` 형식으로 바뀌고 `정상 · 동기화됨`이 된다.
4. dev 주소 `https://homepage-saeoll-dev.<도메인>`에서 확인한다.

> 빌드를 잘못 시작했으면 빌드 이력의 **중지**. dev가 바로 바뀌지 않으면 **3. dev 배포 → Sync** 또는 오른쪽 위 **상태 새로 고침**.

---

### 5-1. 보안 검사 결과 보기

보안 검사가 설치되어 있으면 빌드마다 코드 취약점·비밀정보·라이브러리 취약점·개인정보를 검사한다.

1. 앱 화면 **보안 검사** 단계: 통과(초록) / 경고(노랑) / 차단(빨강). **보고서**를 누르면 상세가 나온다.
2. 메뉴 **품질 관리 → 보안 이슈**에서 우리 업체 앱의 발견 사항을 심각도별로 본다. '내용' 열에 고치는 방법이 있다.
3. 오탐이면 해당 줄의 **예외 요청** → 근거를 적어 요청 → 운영 관리자 승인 후 다음 빌드부터 제외된다.
4. **비밀정보**(비밀번호·키)가 나오면 값을 바로 바꾸고(재발급) 소스에서 지운다. 커밋 이력에 남기 때문이다.
5. 차단 모드에서 기준을 넘으면 빌드는 끝나도 **배포되지 않는다**. 고쳐서 다시 push 한다.

자세한 내용: [보안 검사 · 품질 관리 가이드](security-guide.md) 5장.

## 6. 운영(prod) 배포하기

dev에서 테스트가 끝난 버전을 운영에 올린다.

### 6-1. 릴리스 태그 만들기 (git)

버전은 `v주.부.수` 형식이다(예: `v1.0.0`, 다음 수정은 `v1.0.1`).

```bash
git checkout main && git pull
git merge --no-ff develop
git tag -a v1.0.0 -m "v1.0.0 최초 오픈"
git push origin main --follow-tags
```

### 6-2. 콘솔에서 릴리스 빌드

1. 앱 화면 → **4. 릴리스 → 릴리스**
2. **릴리스 태그**에 `v1.0.0` 입력(기존 태그 목록에서 골라도 된다) → **실행**
3. 빌드 이력에 `릴리스 v1.0.0 실행 중` → **성공**이 되면 **5. prod 배포**가 `변경 있음`, 태그 `v1.0.0`으로 바뀐다.

### 6-3. 운영 관리자에게 배포 요청

prod 배포는 운영 관리자가 승인한다. 아래 양식으로 요청한다.

```text
[운영 배포 요청]
업체/앱   : saeoll / homepage
버전      : v1.0.0  (콘솔 릴리스 빌드 #3 성공)
변경 내용 : 로그인 화면 추가, 게시판 오류 수정
dev 확인  : https://homepage-saeoll-dev.<도메인> 에서 테스트 완료
희망 일시 : 2026-11-03 18:00
롤백 기준 : 로그인 오류 발생 시 v0.9.0 으로
```

배포가 끝나면 앱 화면 **5. prod 배포**가 `정상 · 동기화됨`이 되고, prod 주소에 새 버전이 나온다.

## 7. 문제가 생겼을 때 되돌리기

| 환경 | 방법 |
| --- | --- |
| dev | 잘못된 커밋을 되돌려(`git revert <커밋>`) develop에 push → 자동 재배포 |
| prod | 운영 관리자에게 롤백 요청(되돌릴 버전 명시). 고친 버전은 새 태그(`v1.0.1`)로 릴리스 |

## 8. GitLab 업체라면

외부 업체는 GitLab(`https://gitlab.<도메인>`)을 쓴다. 콘솔 화면은 같고 다음이 다르다.

| 항목 | GitLab 업체 |
| --- | --- |
| 소스·git | `https://gitlab.<도메인>/<업체>/<앱>.git`, git 비밀번호 대신 GitLab **액세스 토큰** ([업체 개발자 가이드 2장](vendor-guide.md#2-pc-준비)) |
| 빌드 | GitLab 파이프라인. develop push 즉시 시작. 콘솔 **빌드 실행**도 가능 |
| 코드 리뷰 | `feature` → `develop` 머지 요청(MR) |
| 릴리스 | PM(Maintainer)이 GitLab에서 태그 `vX.Y.Z` 생성 → 릴리스 파이프라인 자동 실행. 콘솔 **릴리스** 버튼은 운영 관리자만 |
| 빌드 로그 | 콘솔 **로그** 화면 위쪽에서 단계(job)를 골라 본다 |

## 9. 자주 묻는 문제

| 증상 | 해결 |
| --- | --- |
| `git clone` 시 `Authentication failed` | 로그인 비밀번호가 아니라 **git 비밀번호**(2-2)를 입력. Windows는 자격 증명 관리자에서 `scm-manager` 항목 삭제 후 다시 시도 |
| `git clone` 시 403 / `not found` | 저장소 참여자(쓰기)가 아님 → 운영 관리자에게 요청 (먼저 `scm.`에 한 번 로그인) |
| `SSL certificate problem` | 3장 1)의 인증서 등록 확인 |
| `warning: remote HEAD refers to nonexistent ref` | `-b develop` 붙여서 clone |
| push 했는데 빌드가 안 시작됨 | 5분 기다리거나 콘솔 **빌드 실행** |
| 빌드 **실패** | 빌드 **로그**의 마지막 부분에서 `ERROR`/`FAIL` 찾기. 컴파일·테스트 오류는 소스 수정 후 다시 push. `Image` 단계 오류(이미지 push 실패 등)는 운영 관리자에게 로그와 함께 문의 |
| dev가 `오류` | dev 환경 패널의 경고 문구 확인. 대부분 앱이 8080 포트로 뜨지 않거나 `/healthz` 응답이 200이 아님 |
| dev가 `없음` | 아직 첫 빌드가 성공하지 않음 → 빌드 이력 확인 |
| **릴리스** 실행 후 실패 | 태그를 push했는지(`git push origin v1.0.0`), 태그 이름이 `v1.0.0` 형식인지 확인 |
| 콘솔에 우리 업체가 안 보임 | 운영 관리자에게 구성원 추가 요청 → 로그아웃 후 재로그인 |

## 10. 지켜야 할 것

- 비밀번호·접속 키·개인정보를 소스나 커밋 메시지에 넣지 않는다. (SCM 웹 화면은 다른 팀도 소스를 볼 수 있다)
- prod 배포는 반드시 dev 테스트 후 6-3 양식으로 요청한다.
- 태그는 한 번 만든 이름을 다시 쓰지 않는다. 수정본은 번호를 올린다(`v1.0.1`).
